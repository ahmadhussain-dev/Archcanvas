# Floorplan Editor Example Project Architecture (example)

This example project is a Babylon.js-based 2D/3D floorplan editor web application. To eliminate high coupling caused by the original single giant `app.js` (God Object), the application underwent a **progressive modular state refactoring**.

---

## 1. Directory Structure

The refactored directory structure is divided into three core layers, each with single, clear responsibilities:

```
example/
├── type/                  # Static type definition layer (JSDoc Type Definitions)
│   ├── common.js          # Common base types (SelectedTarget, TargetType, etc.)
│   ├── uiState.js         # UI interaction state type definitions
│   ├── selectionState.js  # Selected entity state type definitions
│   ├── editorPreviewState.js # Editor preview and alignment snapping state definitions
│   └── appState.js        # Aggregated main AppState type definitions
│
├── store/                 # Runtime state management layer (Runtime State Stores)
│   ├── index.js           # Single instance export (exports ui, selection, editor singletons)
│   ├── uiStore.js         # Store class managing UI modes, menus, and view states
│   ├── selectionStore.js  # Store class managing selected furniture, doors, windows, room IDs
│   ├── editorPreviewStore.js # Store class managing drawing previews, grid snapping states
│   └── proxyHelper.js     # Proxy state redirection & bridging helper
│
├── js/                    # Business logic handler processors layer (Handler Processors)
│   ├── DragHandler.js     # 2D dragging, room/wall scaling interactions
│   ├── MaterialManager.js # Material library rendering, painting, eyedropper & lock state logic
│   ├── TargetHandler.js   # Context menu actions (duplicate, delete, rotate)
│   ├── SvgEvents.js       # 2D SVG view pointer, wheel, and drawing controls
│   ├── Viewer3DHandles.js # 3D viewport edit gizmos and drag interactions
│   └── EditorUi.js        # Side panel input controls value binding & synchronization
│
└── app.js                 # Engine initialization, 3D rendering main loop & orchestrator
```

## 2. State Management Mechanism

### 2.1 State Redirection & Decoupling
All runtime states are organized into Store singletons inside `store/`. In any business handler, you can directly import the latest state via **ES Modules**:

```javascript
import { ui, selection, editor } from '../store/index.js';

// Read state
if (ui.mode === 'select') {
  console.log('Currently in select mode');
}

// Write state
selection.selectedItemId = 'item_1';
```

### 2.2 Proxy Helper
To ensure **zero code breakage risk** and **complete decoupling of flat appState properties** when refactoring large interaction Handlers, we utilized the proxy sandbox technique in [proxyHelper.js](store/proxyHelper.js):
* **Intercept & Redirect**: Handlers retain reads to `ctx.selectedItemId` or `ctx.mode`, but the Proxy automatically redirects them under the hood to `selection.selectedItemId` and `ui.mode`.
* **Method Passthrough**: Non-state method calls (such as `ctx.pushHistory()`, `ctx.testMap`, etc.) automatically pass through to the original context injected by `app.js`, achieving clean separation of state and methods.

### 2.3 Bidirectional State Sync Loop
Inside `app.js`, the main control logic employs a `syncLocalToStore()` local update function. Triggered automatically at the tail end of core flows like entity selection (`selectTarget`), mode changes (`setDesignMode`), and snapshot restoration:
1. Flat local variables inside `app.js` respond efficiently during calculation.
2. Property data in global independent Stores remains up-to-date for direct reading by all Handlers.

## 3. Development Guidelines

1. **Adding New State Properties**:
   * Do not add global `let` variables at the top of `app.js` or attach fields directly to `appState`.
   * Add properties to constructor methods in the corresponding Store class under `store/` (e.g., `uiStore.js`).
   * Add JSDoc annotations in the corresponding type definitions under `type/` for full IDE autocompletion.

2. **Invoking Engine APIs**:
   * Each Handler is injected with a `ctx` context during initialization (e.g., `initTargetHandler(ctx)`).
   * For operations involving underlying 3D resources (`ctx.viewer3d`, `ctx.scene`, etc.), history management, or global dialogs, call them via `ctx.xxx()`.
